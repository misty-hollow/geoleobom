> **동결 문서.** 이후 Claude Code / Codex 구현의 단일 기준 문서. 제품 범위·기술 스택·14주 일정은 v2에서 동결되었고, v2.1은 Astra 기술 검토(캐시·집계·OSRM·데이터 배포본·표현 정정)만 반영한다. v2.2는 실제 계약한 운영 서버(InterServer, Los Angeles)에 직접 영향받는 부분만 반영했다. **v2.3은 v2.2에서 미정으로 남아 있던 API 표현 의미 4건만 확정한다.** 이 문서와 다른 구현은 문서를 먼저 개정한 뒤 진행한다.
> 전제: 3인 캡스톤 14주 · 핵심 개발 1인(주 20~25h) · Claude Code/Codex 전 과정 활용 · 수십~수백 명 MVP
> 작성일: 2026-09-10 (Week 1) · v2.3 개정일 2026-09-11 (Week 1) · v2 → v2.1 변경 목록은 부록 A · v2.1 → v2.2 변경 목록은 부록 D · **v2.2 → v2.3 변경 목록은 부록 E**
> **v2.1·v2.2 원본은 `docs/걸어봄_확정설계_v2.1.md`·`docs/걸어봄_확정설계_v2.2.md`에 동결 보존한다.** 실제 운영 상태(접속·설정·배포 진행)는 이 문서가 아니라 `STATUS.md`에 기록한다.
>
> **v2.3이 확정한 것은 다음 4건뿐이다** (사용자 승인 2026-09-11): ① 제품 오류 응답 body와 HTTP 상태 매핑 ② `density.count`의 상태별 의미 ③ `nearest[].best`·`top3`의 상태별 표현 ④ `computed_at`의 시각 의미. 모두 v2.2가 정하지 않아 구현이 임의로 메워야 했던 표현 공백이다.
>
> **v2.3이 바꾸지 않은 것**: 제품 범위 · 기술 스택 · 좌표·시간 모델(`[lon, lat]`, 5자리 1회 반올림, k = 5.0/4.5, `time_model_version`) · 후보 추출과 OSRM 규약(3km·20개, 1km·60개 배치, `sources=0`·목적지 ≤160, `--max-table-size 200`) · 캐시 키 · 성능 목표 · 서버 규약 · 14주 일정 · 게이트 항목. 상태값·카테고리·에러 코드의 **집합**도 그대로이며, v2.3은 그 값들이 응답에서 어떻게 나타나는지만 정한다.

## 1. 확정 사항과 근거 (v2 판정 + v2.1 정정)

### 1-1. 프론트·배포: React/Vite 정적 빌드 + 단일 VPS — 확정
- 동적 OG 이미지와 서버 렌더링은 Must가 아니므로 Next.js를 쓰지 않는다. 1인 개발자에게는 배포 대상 하나(같은 도메인 `/api`)가 CORS·환경변수 2벌보다 유리하다.
- 텍스트 OG(Should)는 FastAPI가 `/p/*`, `/c/*` 요청의 `index.html`에 `og:title`·`og:description`을 주입해 처리한다. 공수는 짧을 것으로 예상하나 확정하지 않는다.
- TypeScript 필수. FastAPI OpenAPI 스키마에서 TS 타입을 생성해 계약을 고정한다.

### 1-2. POI 저장: GeoPackage(SQLite) — 확정, 배포본 사양 명시
- POI는 읽기 전용이고 사용자가 서버에 쓰지 않으므로 PostGIS를 두지 않는다.
- **서비스용 GeoPackage는 다음을 반드시 포함한다**: EPSG:4326의 `lon`, `lat` REAL 컬럼, `SPATIAL_INDEX=YES`로 생성된 R*Tree(`rtree_poi_geom`), `rtree_poi_geom.id = poi.fid` 연결. 서버는 geometry BLOB을 해석하지 않고 **R*Tree와 좌표 컬럼만 읽는다**(기본 `sqlite3`에는 `ST_X` 같은 공간 함수가 없다).
- QGIS에서 검수·수정한 뒤에는 정제 스크립트로 서비스 파일을 **다시 생성**해 geometry와 `lon`/`lat`을 일치시키고 `data_version`을 올린다. 서버 파일을 직접 편집하지 않는다.
- 조회 성능은 보장 문구를 두지 않고 Week 2에 실측한다. 사양은 부록 C.

### 1-3. 서비스 지역: 충청권 데이터, 공주 검수 — 확정
- 검수 범위와 데이터 범위는 분리한다. 검수·실측은 공주만 하고, 그 외 충청권은 "미검수 · 예상치"로 표시한다.
- 공주만 지원하면 베타 사용자(천안·대전·세종)가 자기 동네에서 써볼 수 없고, 지원 경계에서 시설·경로가 잘린다. 충청권은 공주 한정과 개발자 작업량 차이가 작을 것으로 예상된다(추출 범위와 CSV 개수 차이).
- **데이터 추출 범위 = 서비스 경계 + 시설 검색 여유(3km) + 경로 우회 여유**(경계 밖으로 돌아가는 경로가 잘리지 않도록 버퍼 포함). 충청권·전국 모두 같은 원칙.
- **전국 전환은 토글이 아니다.** 전국 POI GeoPackage와 전국 OSRM 그래프를 PC에서 사전 생성 → 서버에 새 버전 디렉터리로 업로드 → 자원(10절 메모리 기준)과 대표 결과를 확인 → 데이터셋 교체. 애플리케이션 변경은 작지만 데이터 준비·검증 작업은 남는다. Week 9에 착수 여부를 판단한다.

### 1-4. 캐시: 프로세스 내 TTL 캐시, 격자 반올림 없음 — 확정(정정)
- Redis 없음. uvicorn 워커 1개 + TTL 캐시(TTL 30일, 최대 5,000건).
- **캐시 키 = 계산에 사용한 좌표(5자리 문자열 그대로) + `data_version` + `time_model_version`.** v2의 "4자리 격자 키"는 삭제한다. 이 변경은 담장·하천 주변의 스냅 오류를 없애지는 않지만, **서로 다른 계산 입력이 같은 결과를 공유하는 오류**를 없앤다.
- 요약 결과만 캐시한다. 경로 geometry는 캐시하지 않는다.
- 데이터·시간 모델을 바꾸면 버전이 키에 포함되어 이전 항목은 자연히 미스가 된다. 재시작 시 캐시가 비는 것은 허용한다.

### 1-5. 경사 보정: 실험 먼저, 참고값부터 — 확정(정정)
- 경사 보정 계산(경로 geometry + DEM 샘플링 + Tobler)은 GIS 담당이 Jupyter에서 AI 도움을 받아 수행한다. 개발자 시간은 거의 들지 않을 것으로 예상되나 확정하지 않는다.
- Week 6 실측 30건과 Week 10 확인 실측이 검증 데이터다. **채택 결정은 Week 10 확인 실측 결과를 본 뒤** 내린다.
- **채택하더라도 이번 학기 적용 범위는 경로 상세 화면의 참고 보정시간까지다.** 선택된 경로만 사후 보정하고 최근접 순위·10분 집계가 보정된 것처럼 표시하지 않는다. 핵심 지표는 기존 시간 모델(k 단일 계수)을 유지한다.
- 오차가 줄지 않으면 "SRTM 30m로는 도심 경사 보정이 오차를 줄이지 못했다"가 발표 결과가 된다.

### 1-6. 총점·가중치 제외, 비교 강조 규칙 — 확정(정정)
- 총점과 슬라이더는 만들지 않는다. 거리감쇠 지수 설계는 보고서의 향후 과제로 서술한다.
- **비교 강조 규칙**: 시간 항목은 **최솟값**, 시설 수 항목은 **최댓값**을 강조한다. `20+`끼리는 우열을 정하지 않는다. `집계 미완료`·`불확실`·`도달 불가`·`후보 없음` 상태인 셀은 강조 대상과 "우세 항목 N개" 계산에서 제외한다.

### 1-7. Play/TWA: Could, PM 선행 — 확정
- Must에서 제외. 개발자 시간이 들지 않는 준비(Play 개발자 계정, 개인정보처리방침 페이지 문안, 테스터 15명 명단)는 PM이 Week 1부터 진행한다.
- 개발자는 Week 9 게이트(Week 8 베타 치명 버그 0)를 넘었을 때만 Bubblewrap 작업을 하며, 약 1일로 추정한다. 이후 웹 배포가 곧 앱 업데이트다.
- TWA 진행 여부는 VPS 메모리와 무관하다.

### 1-8. 서버: 4GB VPS 1대 — 확정(실제 계약 반영)
- **계약 서버: InterServer KVM Linux VPS Slice, 2 slices — 1 core · 4GB RAM · 80GB SSD · 월 전송량 4TB · Los Angeles(lax1) · Ubuntu 24.04 64-bit · US$6/월, 1개월 청구.** 이 문서에는 사양·계약 기준만 기록한다.
- 충청권 시작 사양으로 4GB 1대를 택한다. **구성요소별 메모리 사용량은 실측 전이므로 문서에 수치를 확정하지 않는다.** 통과 기준은 10절의 부하 중 `MemAvailable` 약 1GB다.
- 스왑 2GB 설정. OSRM·API는 외부 포트 매핑을 만들지 않는다(5절).
- 현재 계약 서버를 기준으로 진행하며 추가 저가 VPS 비교는 하지 않는다.
- **해외 리전(Los Angeles)이므로 한국 내 클라이언트 환경에서 `/api/search`, `/api/analyze`와 실제 주요 흐름의 응답시간을 게이트 2에서 실측하고, 측정 위치·네트워크 종류를 기록한다.** 측정 전 지연 수치는 문서에 확정하지 않는다.
- **1 vCPU가 게이트 2의 성능·자원 기준을 통과하지 못하면 성능 목표를 낮추지 않고 VPS 증설(slice 추가 또는 상위 플랜) 여부를 판단한다.** 해외 리전 네트워크 지연이 원인인 경우는 증설로 해결된 것으로 취급하지 않으며, 서버 리전 변경은 별도 문서 개정 사항이다. CDN·다른 공급자·아키텍처 변경은 v2.2 범위가 아니다.

### 1-9. 일정: Week 6 핵심 / Week 8 베타 / 실측 Week 6 — 확정
- 1인 개발 전제에서 Week 6 핵심 완성, Week 8 베타, Week 11 여유 주차를 유지한다.
- 실측은 Week 6. 오차 유형(골목 누락, 캠퍼스 출입구, 폐업)이 Week 7 수정의 입력이다.

## 3. 최종 제품 범위 (동결)

### 서비스 정의
"이 집, 걸어서 살 만해?" — 위치 하나를 검색·핀으로 넣으면 편의점·마트·슈퍼, 약국, 의료기관, 공원까지 **보행망 기준** 예상 도보시간과 도보 10분 내 카페·음식점 수를 보여주고, 후보를 4곳까지 담아 비교·URL 공유하는 반응형 웹앱.

### 완료 기준
> 사용자가 두 후보의 위치를 입력하고, 생활시설 접근성을 확인한 뒤, 저장·비교 결과를 다른 사람에게 URL로 전달할 수 있다. 도움 없이, 모바일에서, 2분 안에.

### 4-2. 좌표·시간·버전 규약
- **좌표계·순서**: EPSG:4326. 내부(API·계산·캐시 키·GeoPackage 조회)는 `[lon, lat]`. URL `/p/{lat},{lng}`와 카카오 SDK의 `(lat, lng)`는 **입출력 경계에서 명시적으로 변환**한다.
- **좌표 정밀도**: 검색·핀에서 받은 좌표를 **입력 시점에 한 번만** 소수 5자리로 반올림한다. 그 값이 계산·URL·localStorage·캐시 키에 동일하게 쓰인다. 이후 어떤 단계에서도 다시 반올림하지 않는다.
- **시간 모델**: `service_seconds = osrm_duration_seconds × k`, **k = 5.0 / 4.5**(OSRM foot 기본 5.0 km/h를 4.5 km/h 상당으로). k는 단일 양의 계수라 최근접 순위를 바꾸지 않는다. OSRM `weight`를 시간으로 쓰지 않고, 거리÷속도를 별도 계산해 섞지 않는다. foot 프로필에는 노면·회전 페널티가 있으므로 "모든 구간 4.5 km/h 등속"이라고 설명하지 않는다.
- **10분 판정**: 표시용 반올림 전 `service_seconds ≤ 600`.
- **표시**: 거리 미터 정수, 시간 분 반올림.
- **버전**: `data_version`(POI 기준일 + OSRM 그래프 빌드 ID, 예 `2026Q3-cc-01`), `time_model_version`(프로필 버전 + k, 예 `tm1`). 두 값은 응답과 캐시 키에 항상 포함한다. 실측 후 k를 바꾸면 `time_model_version`을 올린다.

### 4-3. 분석 알고리즘 (확정)
1. **입력 정규화·지역 확인** — 좌표를 `[lon, lat]` 5자리로 확정. 충청권 폴리곤 밖이면 `OUT_OF_REGION`.
2. **캐시 조회** — 키 `analyze:{data_version}:{time_model_version}:{lon}:{lat}`. 히트면 요약 결과 반환.
3. **출발지 스냅** — OSRM `/nearest`. 스냅 실패는 `SNAP_FAILED`. 스냅 거리 > 100m는 `snap_warning` 플래그를 세우고 계산은 진행.
4. **후보 추출** — R*Tree bbox 조회 → `lon`/`lat`로 정확한 직선거리(haversine) 계산 → 반경 필터 → 거리순 정렬.
   - 최근접형 5항목: 직선 3km 내 **항목당 상위 20개**(합계 ≤ 100)
   - 밀도형(카페·음식점): 직선 1km 내 후보 전체를 거리순 목록으로 확보하고 **첫 60개**만 첫 배치에 포함
5. **첫 `/table` 호출** — 최근접 후보 ≤100 + 밀도 첫 배치 60을 합치고 `fid` 중복 제거. **FastAPI가 목적지 수 ≤160을 강제**(초과 시 밀도 배치를 줄여 맞춘다). 요청: `coordinates = [출발지] + 목적지`, `sources=0`, `destinations=1;2;…;N`(명시 필수), `annotations=duration,distance`. **`fallback_speed` 사용 금지.** OSRM은 `--max-table-size 200`으로 기동한다(제한 검사는 `sources×destinations > 값²`이므로 1×160은 통과하지만, `sources`/`destinations`를 생략하면 161×161 행렬이 되어 초과한다).
6. **시간·실패 처리** — 각 목적지 `service_seconds = duration × k`. `duration == null`은 **도달 불가**. `destinations[].distance`(목적지 스냅 거리)가 100m를 넘는 POI는 **스냅 의심**으로 분류해 최근접 선택과 10분 집계에서 제외한다. 스냅 불가·의심 POI 하나가 전체 분석을 실패시키지 않도록 항목 단위로 분리 처리한다.
7. **최근접형 선택** — 유효 후보 중 `service_seconds` 최소 1개를 `best`, 상위 3개를 `top3`로. 항목 `status`: 유효 후보가 있으면 `ok`; 스냅 의심 POI 중 직선거리가 `best`의 보행거리보다 짧은 것이 있으면 `uncertain`; 유효 후보 전부 도달 불가면 `unreachable`; 반경 내 후보 자체가 없으면 `none`. `straight_m × 1.5 ≤ walk_m`이면 `detour_flag`.
   - **상태 경계 (v2.3 확정).** 위 네 상태는 다음 순서로 판정한다. 새 상태값은 만들지 않는다.
     1. 반경 내 후보 자체가 없으면 → `none`.
     2. 반경 내 후보는 있으나 **전부 목적지 스냅 의심으로 제외되어 평가할 유효 후보가 하나도 없으면** → `uncertain`. 경로가 없다고 확인한 것이 아니라 스냅 신뢰 문제로 판단할 수 없는 상태이므로 `unreachable`로 표시하지 않는다.
     3. 평가 가능한 후보가 있으나 그 `duration`이 모두 `null` 등으로 **실제 도달 가능한 유효 경로가 하나도 없으면** → `unreachable`.
     4. 유효 후보가 있고, 스냅 의심 POI 중 직선거리가 `best`의 보행거리보다 짧은 것이 있으면 → `uncertain`(아래 4-4의 A 유형). 그렇지 않으면 → `ok`.
   - `best`·`top3`의 상태별 값 모양은 4-4에 있다.
8. **밀도 집계 완결** — 첫 배치에서 `≤600s`인 시설을 센다. **20곳 도달 → `capped`(`20+`) 즉시 종료.** 20 미만이고 1km 내 남은 후보가 있으면 **다음 60개 배치로 `/table` 추가 호출**하고 반복한다. 남은 후보가 없을 때만 `complete`와 정확한 개수를 반환한다. 총 시간 예산(초기값 5초) 초과·배치 오류·스냅 문제로 끝내지 못하면 `incomplete`(`집계 미완료`)를 반환하고 **절대 0으로 대체하지 않는다.** k를 바꾸면 1km 사전 반경의 충분성(10분 × 4.5 km/h ≈ 750m 보행)을 재확인한다.
   - **`count` 값 (v2.3 확정).** `complete`이면 정확한 개수(0 이상 정수), `capped`이면 `count == cap == 20`, `incomplete`이면 `count == null`이다. **`incomplete`일 때 중간까지 센 부분값을 `count`에 넣지 않는다.** 진행 정도는 `candidates_checked`·`candidates_total`이 담당한다.
   - **`incomplete`는 오류 응답이 아니다 (v2.3 확정).** 최근접 등 핵심 결과가 완성됐는데 밀도 추가 배치만 시간 예산 초과나 배치 timeout으로 끝내지 못한 경우, 응답을 오류로 바꾸지 않고 **HTTP 200 + `density.status = incomplete`** 를 반환한다. 위 `incomplete` 규칙 자체는 v2.2와 같다.
9. **응답·캐시** — 요약 결과를 조립해 반환하고 캐시한다. 호출 횟수 설명 문구: **"보통 한 번 호출, 밀도 집계에 필요한 경우만 추가 호출."**
10. **경로 상세(지연)** — 항목 탭 시 `/route`로 출발지→선택 POI 경로를 가져온다. `/table`과 같은 그래프·스냅 지점·k를 사용한다. 경사 참고값이 채택되면 이 응답에만 별도 필드로 붙는다.

### 4-4. API 계약 (필드명 확정 — 이름 변경은 문서 개정 사항)
**`GET /api/analyze?lon=&lat=`**
| 필드 | 내용 |
|---|---|
| `input` | `lon`, `lat` (계산 좌표, 5자리) |
| `snapped` | `lon`, `lat`, `snap_distance_m` |
| `region` | `supported`(bool), `label`, `verified_area`(bool, 실측 검증 배지) |
| `versions` | `data_version`, `time_model_version`, `poi_date` |
| `warnings` | 배열: `snap_warning` 등 |
| `nearest[]` | `category`(`convenience`/`grocery`/`pharmacy`/`medical`/`park`), `status`(`ok`/`uncertain`/`unreachable`/`none`), `best{fid,name,walk_seconds,walk_m,straight_m,detour_flag}`, `top3[]` |
| `density` | `category`(`food_cafe`), `status`(`complete`/`capped`/`incomplete`), `count`, `cap`(20), `candidates_checked`, `candidates_total` |
| `computed_at` | ISO 시각 |

**`nearest[].best`·`top3` 표현 (v2.3 확정).** 두 필드는 **항상 응답에 존재한다.** `best`는 `Facility | null`, `top3`는 배열이며 `null`이 될 수 없다(비면 `[]`). 상태 경계 판정은 4-3 7단계에 있다.

| `status` | `best` | `top3` | 의미 |
|---|---|---|---|
| `ok` | 유효 후보 중 `service_seconds` 최소 1개 | 유효 후보 보행시간 상위 1~3개. **`top3[0] == best`** | 정상 |
| `uncertain` (A) | 존재 | 1~3개. **`top3[0] == best`** | 유효 후보는 있으나 스냅 의심 POI가 더 가까울 수 있어 결과가 불확실 |
| `uncertain` (B) | `null` | `[]` | 반경 내 후보는 있으나 **전부 스냅 의심으로 제외**되어 평가할 유효 후보가 없음. 도달 불가를 확인한 것이 아니므로 `unreachable`이 아니다 |
| `unreachable` | `null` | `[]` | 평가 가능한 후보가 있었으나 실제 도달 가능한 유효 경로가 없음 |
| `none` | `null` | `[]` | 반경 내 후보 자체가 없음 |

`uncertain`(B)·`unreachable`·`none`은 값 모양이 같다. **의미 차이는 `status`가 보존하며, 클라이언트는 값 모양이 아니라 `status`로 구분한다.**

**`density.count` (v2.3 확정).** 응답에 **항상 존재하는 필수 nullable 필드**다. `complete` → 0 이상 정수, `capped` → `count == cap == 20`, `incomplete` → `null`. 부분값을 넣지 않으며 진행 정도는 `candidates_checked`·`candidates_total`이 나타낸다 (4-3 8단계).

**`computed_at` (v2.3 확정).** **timezone-aware UTC ISO 8601** 문자열이며, 응답을 만든 시각이 아니라 **실제 분석 계산이 수행된 시각**이다. 캐시 미스에서 생성하고, **캐시 히트에서는 새 요청 시각으로 교체하지 않고 원 계산 결과의 값을 그대로 반환한다.** 예: `2026-09-11T03:11:23Z`. 초 단위 이하 정밀도(마이크로초 포함 여부)는 계약으로 고정하지 않는다.

**`GET /api/route?lon=&lat=&fid=`** → `geometry`(GeoJSON LineString), `walk_seconds`, `walk_m`, `snapped_origin`, `snapped_dest`, (`slope_ref_seconds` — 채택 시에만)

**`GET /api/search?q=`** → 카카오 결과 축약 `{name, address, lon, lat}[]`. 서버 저장 없음.

**에러 코드**: `OUT_OF_REGION`, `SNAP_FAILED`, `OSRM_ERROR`, `TIMEOUT`, `RATE_LIMITED`, `TOO_MANY_DESTINATIONS`(내부 가드 위반 — 발생 시 버그).

**제품 오류 응답 계약 (v2.3 확정).** body는 **평면 두 필드**다. 중첩 error envelope를 두지 않는다.

```json
{ "code": "OUT_OF_REGION", "message": "현재 충청권만 지원합니다" }
```

- `code`는 위 **6종 중 하나**다. v2.3은 새 에러 코드를 만들지 않는다.
- `message`는 문자열이다. **문구 자체는 안정 API 계약이 아니다** — 문구는 예고 없이 바뀔 수 있다.
- **프론트 로직은 `message`가 아니라 `code`로 분기한다.**

| `code` | HTTP |
|---|---|
| `OUT_OF_REGION` | 400 |
| `SNAP_FAILED` | 400 |
| `RATE_LIMITED` | 429 |
| `TOO_MANY_DESTINATIONS` | 500 |
| `OSRM_ERROR` | 502 |
| `TIMEOUT` | 504 |

`TOO_MANY_DESTINATIONS`는 4-3 5단계의 **내부 가드 위반이므로 발생 자체가 버그**라는 의미를 유지한다(그래서 5xx다).

**`TIMEOUT`의 경계.** 요청의 **필수 결과**를 완성하기 위한 상류 호출이 timeout되어 그 요청을 정상 완료할 수 없으면 `TIMEOUT`(504)이다. **단, `/api/analyze`에서 최근접 등 핵심 결과는 완성됐고 밀도 추가 배치만 시간 예산 초과·배치 timeout으로 끝내지 못한 경우는 오류가 아니다** — HTTP 200 + `density.status = incomplete`로 반환한다(4-3 8단계). 이는 v2.2의 밀도 `incomplete` 규칙을 약화하지 않는다.

**계약 밖.** FastAPI가 쿼리 검증 실패에 자체적으로 만드는 **422 응답은 이 6종 제품 오류 계약에 포함되지 않으며**, 그 기본 `detail` 형식도 제품 API 오류 body로 간주하지 않는다. `/api/search`의 카카오 고유 실패 의미, `/api/route`의 존재하지 않는 `fid` 등 현재 6종으로 표현되지 않는 상황에 대한 **새 오류 코드는 v2.3에서 만들지 않는다.**

### 4-5. 프론트 표시 규칙
- `status != ok`인 최근접 항목은 시간 대신 상태 문구("도달 경로 없음", "확인 필요", "반경 내 없음")를 표시한다.
- 밀도 `capped` → `20+`, `incomplete` → `집계 미완료`(회색), `complete` → 숫자.
- **표시 분기는 값이 아니라 `status`로 결정한다 (v2.3 확정).** `count == null`이나 `best == null` 같은 값 모양에서 상태를 역추론하지 않는다. `uncertain`(B)·`unreachable`·`none`은 값 모양이 같지만 표시 문구가 다르고, `20+`는 `count`가 20이라서가 아니라 `status == capped`이기 때문에 표시한다. 오류 응답도 `message`가 아니라 `code`로 분기한다(4-4).
- 비교표는 1-6 규칙을 그대로 구현한다.
- 모든 화면에 `poi_date`와 "예상 시간" 문구를 노출한다.

## 부록 B. PROJECT.md에 고정할 규약 (Week 1, 이 문서와 일치해야 함)
- 좌표: EPSG:4326. 내부 `[lon, lat]`. URL `/p/{lat},{lng}`·카카오 SDK `(lat,lng)`는 경계에서 변환. 입력 시 5자리 1회 반올림, 이후 재반올림 금지.
- 시간: `service_seconds = osrm_duration × k`, k = 5.0/4.5 (`time_model_version = tm1`). 600초 판정은 반올림 전. 표시는 분 반올림, 거리는 m 정수.
- 캐시: 키 `analyze:{data_version}:{time_model_version}:{lon}:{lat}`, TTL 30일, 5,000건, 요약만.
- OSRM: 이미지 태그 고정(PC=서버), `--algorithm mld --max-table-size 200`. `/table`은 `sources=0`, `destinations` 명시, `annotations=duration,distance`, `fallback_speed` 금지. 목적지 ≤160(FastAPI 가드).
- 후보: 최근접형 직선 3km·항목당 20개. 밀도형 직선 1km 전체 목록, 배치 60개, 시간 예산 5초.
- 상태: 최근접 `ok/uncertain/unreachable/none`, 밀도 `complete/capped/incomplete`. `incomplete`를 0으로 표시 금지.
- 스냅: 출발지 >100m 경고 플래그, 목적지 >100m 스냅 의심 제외.
- 비교 강조: 시간 최솟값, 시설 수 최댓값, `20+` 무강조, 비정상 상태 셀 제외.
- 항목 코드: `convenience`, `grocery`, `pharmacy`, `medical`, `park`, `food_cafe`. 표시명·업종코드 매핑표 파일 위치.
- 지원 지역 폴리곤 파일 위치·버전. 실측 검증 구역 폴리곤 위치.
- 데이터: `/srv/geoleobom/data/{data_version}/` 구조, 교체 절차(5절), 직전 버전 보존.
- 로그: 좌표 원문·검색어·`/p/*` 파라미터·쿼리 문자열 기록 금지.
- 금지: 서버에서 빌드·전처리, `.env` 커밋, 신생 라이브러리, 문서에 없는 필드명·에러 코드 추가.

**응답 표현 불변식 (v2.3 추가).** 위 규칙은 그대로 두고 아래를 더한다. 구현자가 바로 검사로 옮길 수 있는 최소 형태다.

- `density.status == capped` ⇒ `density.count == density.cap == 20`
- `density.status == incomplete` ⇒ `density.count is null` (부분값 금지, 0 대체 금지)
- `density.status == complete` ⇒ `density.count`는 0 이상 정수
- `nearest[].status in {none, unreachable}` ⇒ `best is null` 그리고 `top3 == []`
- 반경 내 후보가 모두 스냅 의심으로 제외 ⇒ `status == uncertain`, `best is null`, `top3 == []` (`unreachable` 아님)
- `nearest[].status == ok` 또는 `uncertain`(A, `best` 있음) ⇒ `top3`는 1~3개이고 `top3[0] == best`
- `best`·`top3`·`count`는 항상 응답에 존재한다. `top3`는 `null`이 될 수 없다(비면 `[]`)
- 밀도 추가 배치만 실패·예산 초과 ⇒ 오류 응답이 아니라 HTTP 200 + `incomplete`
- 제품 오류 body는 `{code, message}` 평면 두 필드. `code`는 위 6종. HTTP 매핑은 4-4 표. FastAPI 422는 이 계약 밖
- `computed_at`은 UTC aware ISO 8601이며 캐시 히트 시 원 계산 시각을 그대로 반환

## 부록 E. v2.2 → v2.3 변경 목록

v2.3은 v2.2가 정하지 않아 구현이 임의로 메워야 했던 **API 표현 의미 4건만** 확정한다. 사용자 승인 2026-09-11("4개 결정 승인, v2.3 진행"). v2.2 원본은 `docs/걸어봄_확정설계_v2.2.md`에 동결 보존한다.

| # | 항목 | v2.2 | v2.3 | 반영 위치 |
|---|---|---|---|---|
| 1 | 제품 오류 응답 body | 에러 코드 6종만 나열. body 형식·HTTP 상태 미정 | 평면 `{code, message}`. `code`는 기존 6종. `message`는 안정 계약 아님(프론트는 `code`로 분기). HTTP: `OUT_OF_REGION`·`SNAP_FAILED` 400, `RATE_LIMITED` 429, `TOO_MANY_DESTINATIONS` 500, `OSRM_ERROR` 502, `TIMEOUT` 504. `TIMEOUT`은 필수 결과를 완성 못 한 경우이며 밀도 배치만 실패하면 200+`incomplete`. FastAPI 422는 계약 밖 | 4-4, 4-3 8단계, 부록 B |
| 2 | `density.count` | 필드명만 있고 상태별 값 미정 | 항상 존재하는 필수 nullable. `complete` → 0 이상 정수, `capped` → `count == cap == 20`, `incomplete` → `null`(부분값 금지). 진행 정도는 `candidates_checked`·`candidates_total` | 4-4, 4-3 8단계, 부록 B |
| 3 | `nearest[].best`·`top3` | 상태 4종은 있으나 `best`·`top3`의 값 모양 미정 | 둘 다 항상 존재. `best: Facility \| null`, `top3`는 배열(`null` 금지). `ok`·`uncertain`(A) → `best` 존재·`top3` 1~3개·`top3[0] == best`. 후보 전부 스냅 의심 → `uncertain`(B), `best = null`, `top3 = []` (`unreachable` 아님). `unreachable`·`none` → `best = null`, `top3 = []`. 의미 차이는 `status`가 보존 | 4-4, 4-3 7단계, 4-5, 부록 B |
| 4 | `computed_at` | "ISO 시각"만 명시 | timezone-aware UTC ISO 8601. **실제 분석 계산 시각**이며 캐시 미스에서 생성. 캐시 히트는 원 계산 값을 그대로 반환(요청 시각으로 교체 금지). 초 단위 이하 정밀도는 계약으로 고정하지 않음 | 4-4 |

**v2.3에서 바뀌지 않은 것**: 제품 범위(3절), 기술 스택(4-1), 좌표·시간·버전 규약(4-2 — `[lon, lat]`, 5자리 1회 반올림, k = 5.0/4.5, `time_model_version`, 600초 판정), 후보 추출·OSRM 규약(4-3 4·5단계), 캐시 키(4-3 2단계), 밀도 `incomplete` 규칙 자체, 성능 목표와 게이트(10절), 서버 구성(5절), Must/Should/Could/Won't(6절), 14주 일정(8절), 비용(9절). **상태값·카테고리·에러 코드의 집합도 그대로이며, v2.3은 그 값들이 응답에서 어떻게 나타나는지만 정한다.**

**v2.3이 일부러 정하지 않은 것**: `/api/search`의 카카오 고유 실패 의미, `/api/route`의 존재하지 않는 `fid` 처리 등 현재 6종으로 표현되지 않는 상황의 새 오류 코드. 필요해지면 별도 개정 사항이다.
