# 걸어봄 개발 운영 가이드

작성일: 2026-09-10 · 기준: 첨부 「걸어봄_확정설계_v2.1(2).md」

이 문서는 제품·기술 설계를 바꾸는 문서가 아니다. v2.1을 구현할 때 사용할 작업 방식이다. 프로젝트 코드나 설정 파일은 이번 요청에서 작성하지 않았다.

**권장 방식은 VS Code 안에서 Claude Code가 한 작업을 구현하고, 중요한 변경만 Codex가 독립 검토하며, 본인이 실제 결과를 확인해 채택하는 것이다. ChatGPT Project는 이해와 진단을 돕는 보조 공간으로 쓴다. 작업 기준과 현재 상태는 Git 저장소에 둔다.**

모든 코드를 읽을 필요는 없다. 대신 매번 “무엇이 달라졌고, 어떤 입력에서 무엇이 나와야 하며, 실제로 그렇게 나왔는가”를 설명할 수 있어야 한다.

**1. 가장 먼저 막을 위험**

가장 큰 위험은 코드를 작성하지 못하는 것이 아니라, 잘못된 계산이나 데이터 처리가 그럴듯한 화면과 테스트 뒤에 숨어 며칠 동안 쌓이는 것이다. AI 두 개가 동의하더라도 같은 설계를 잘못 해석했으면 함께 틀릴 수 있다.

| 실제 위험 | 걸어봄에서 나타나는 모습 | 기본 대응 |
|---|---|---|
| 구현과 테스트가 같은 오해를 공유 | 600초 경계나 밀도 집계가 틀렸는데 테스트는 통과 | 구현 전에 사람이 확인한 기대 결과를 정한다. 수학·규칙 검사와 실제 데이터 검사를 구분한다. |
| 작업이 커져 원인을 잃음 | 검색·지도·분석·저장을 한 번에 바꾸고 어디서 깨졌는지 모름 | 진행 중 구현 작업은 하나. 검수까지 반나절 안에 끝낼 수 있는 크기로 나눈다. |
| 모델·환경·데이터의 기준이 달라짐 | Claude와 Codex가 다른 계약을 사용하거나, PC에서 검수한 데이터와 서버 데이터가 다름 | 저장소의 공통 지침과 v2.1을 읽게 한다. 배포마다 코드·데이터·시간모델 버전을 기록한다. |
| 수정 반복이 검증을 대체 | 에러가 나면 패키지 업그레이드·설정 변경·재설치를 연달아 수행 | 같은 실패가 두 번 반복되면 수정을 멈추고 재현·관찰 단계로 전환한다. |

이번 운영 방식은 이 네 가지를 줄이는 데 집중한다. 별도의 개발 관리 서비스나 여러 대의 서버는 필요하지 않다.

**2. 개발 공간과 역할을 이렇게 고정한다**

| 도구·사람 | 기본 역할 | 결과를 받아들이는 기준 |
|---|---|---|
| VS Code | 코드·변경 내역·실행 결과를 보는 하나의 작업 공간 | 어느 프로젝트 폴더와 브랜치를 열었는지 확인할 수 있다. |
| Claude Code | 기본 구현 담당. 코드·관련 테스트·문서 수정·실행·일반 오류 수정까지 수행 | 작업 카드의 완료 조건과 실제 검사 결과를 제출한다. |
| Codex | 계산·데이터·API 계약·배포 변경의 독립 검토. 필요하면 구현 담당 대체 | 구체적인 반례, 영향받는 코드, 실행한 검사와 미실행 검사를 구분해 제출한다. |
| ChatGPT Project | 개념 설명, 진단 결과 해석, 선택지 판단 | 현재 자료에서 확인한 사실과 추측을 구분하고, 다음 확인 행동을 제시한다. |
| 본인 | 작업 목표·기대값·채택·병합·배포 결정 | 화면 또는 응답을 직접 확인하고, 변경 이유와 실패 시 대응을 설명한다. |
| B: 데이터·GIS | 시설·분류·통행 가능성·실측의 현실 검증 | 검수한 데이터 버전, 위치, 근거, 수정 사항을 남긴다. |
| C: QA·PM | 실제 사용자 흐름 검증·문제 재현·일정 관리 | 어떤 버전에서 무엇을 했고 무엇이 잘못됐는지 재현 가능하게 보고한다. |

Claude를 기본 작성자로 정한 것은 운영상 기본값이다. 절대적인 성능 우열을 뜻하지 않는다. 첫 1~2주 동안 사용 한도·설치 안정성·본인과의 작업 편의성을 보고 Codex와 역할을 한 번 바꿔도 된다. 그 후에는 작업마다 도구를 바꾸기보다 정해진 역할을 유지한다.

두 에이전트가 같은 작업 폴더를 동시에 수정하지 않게 한다. 검토를 시작하면 작성자를 멈추고, 고정된 변경 내역을 Codex에게 준다. Codex가 대신 수정할 때에는 구현 담당을 넘겼다고 명시한다. 처음에는 에이전트 병렬 실행이나 여러 작업 폴더를 운용하지 않는다.

둘 다 공식 VS Code 확장을 제공하므로, 처음부터 별도 코딩 앱·클라우드 실행 환경·CLI를 모두 익힐 필요는 없다. 확장을 기본으로 쓰고, 꼭 필요한 기능이 있을 때만 VS Code의 터미널을 사용한다. [Codex IDE 문서](https://learn.chatgpt.com/docs/codex/ide), [Claude Code VS Code 문서](https://code.claude.com/docs/en/vs-code)

설치할 때에는 AI에게 먼저 운영체제, 메모리, 남은 디스크, 기존 Git·Node·Python·Docker 설치 상태를 읽기 전용으로 확인하게 한다. 버전과 실제 실행 경로를 기록한 뒤 필요한 것만 설치한다. Windows에서는 걸어봄의 Linux 도구를 쓰기 위해 WSL2를 선택할 수 있지만, 기존에 잘 동작하는 개발 환경까지 무조건 바꾸지는 않는다. 선택한 환경 안에 프로젝트와 실행 도구를 모아 Windows·WSL의 Python이나 Git을 번갈아 사용하지 않는다. Codex 자체는 Windows 기본 환경에서도 사용할 수 있다. [Codex Windows 문서](https://learn.chatgpt.com/docs/windows/windows-sandbox)

이미 사용할 수 있는 구독 계정으로 로그인하는 구성을 먼저 사용한다. 새로운 API 과금, 추가 사용량 자동 결제, 유료 속도 옵션을 기본 설정으로 켜지 않는다. 한도에 걸리면 진행 상태를 기록하고 다른 도구로 담당을 넘긴다.

**3. 문서는 기존 설계와 작은 운영 파일만 둔다**

저장소는 프로젝트 파일과 변경 이력을 함께 보관하는 곳이다. Git은 내 PC의 이력을 관리하고, GitHub는 그 이력을 원격에 보관하고 변경 내용을 검토하는 공간으로 사용한다.

| 파일 | 담을 내용 | 갱신 시점 |
|---|---|---|
| v2.1 원문 | 동결된 제품·계산·API·배포 규약 | 본인이 승인한 정정이 있을 때만 |
| `PROJECT.md` | 설계 관련 절을 찾아가는 안내, 구현 규약 요약, 폴더 역할, 선택한 버전, 승인된 구현 결정 | 계약·환경·중요 결정 변경 때 |
| `AGENTS.md` | 두 AI가 따를 작업 규칙, 실행·검사 안내, 승인 경계, 완료 보고 형식 | 실제 반복 문제가 생겨 규칙이 필요할 때 |
| `CLAUDE.md` | `AGENTS.md`를 가져오는 연결만 | 초기 설정 이후 거의 없음 |
| `README.md` | 설치·실행·기본 검사·배포·이전 버전 복구 방법 | 명령이나 작업 절차가 바뀔 때 |
| `STATUS.md` | 지금 동작하는 것, 현재 작업 하나, 막힌 점, 다음 작업 하나 | 작업 종료 때 5~10줄로 |

v2.1 전체를 여러 파일에 복제하지 않는다. `PROJECT.md`에는 중요한 규약을 요약하되 원문 절을 연결한다. 현재 상태를 설계 문서나 AI의 자동 기억에 섞지 않는다. `README.md`에는 AI가 실제로 실행해 확인한 명령만 적는다. 아직 실행하지 못한 것은 ‘미확인’으로 표시한다.

Codex는 `AGENTS.md`를 읽고, Claude Code는 `CLAUDE.md`에서 다른 파일을 가져올 수 있다. 따라서 공통 규칙을 하나만 관리할 수 있다. 처음 설정한 뒤 두 도구에 각각 “읽은 지침 파일과 이번 작업의 제한을 요약해 달라”고 요청해 확인한다. [Codex AGENTS.md 문서](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [Claude Code 공통 지침 가져오기](https://code.claude.com/docs/en/memory#agentsmd)

작업 목록과 버그는 GitHub Issues 한 곳에 둔다. Issue는 할 일이나 버그를 한 장으로 기록하는 카드다. 별도의 Jira·Notion 보드와 중복 관리하지 않는다. 전체 14주의 세부 작업을 미리 수십 장 작성하지 말고, 주간 목표와 다음 2~3개 작업만 구체화한다.

설계에 빈칸이나 모순이 나오면 AI에게 추측해서 채우게 하지 않는다. 해당 문장, 실제로 필요한 행동, 가장 작은 수정안을 카드에 남긴다. 기존 규약 안의 함수·파일 분리는 AI가 결정한다. API 필드·에러 코드·계산 결과의 의미·저장 데이터·기술 스택을 바꾸는 결정은 본인이 승인하고 문서를 먼저 정정한다. C는 범위와 일정 영향을 함께 확인한다.

공통 지침에는 다음 정도면 충분하다.

- v2.1과 관련 규약을 읽고 현재 작업 하나만 수행한다.
- 승인된 작업 안의 코드 수정·검사·일반 오류 수정은 이어서 수행한다.
- 관련 없는 정리, 패키지 일괄 업그레이드, 새 서비스 추가를 하지 않는다.
- 테스트를 통과시키려고 기대값을 임의로 바꾸거나 검사를 끄지 않는다.
- 실제 결과와 모의 결과, 실행한 검사와 미실행 검사를 구분한다.
- 비밀키를 채팅·로그·Git에 넣지 않는다.
- 외부 배포·실데이터 교체·삭제·새 비용은 구체적 대상과 복구 방법을 제시한 뒤 승인받는다.
- 완료 때 변경 내용, 검사 결과, 미확인 사항, 사람이 확인할 행동을 짧게 보고한다.

**4. 매일 반복할 작업 한 바퀴**

작업 크기는 코드 줄 수로 판단하지 않는다. ‘내가 검수까지 한 번의 작업 시간 안에 마칠 수 있는가’가 기준이다. 처음에는 1~3시간을 목표로 잡고, 반나절이 넘어갈 것 같으면 나눈다. 이 시간은 보장 공수가 아니라 작업을 쪼개기 위한 기준이다.

‘분석 기능 전체 구현’은 너무 크다. ‘보정된 시간이 600초 이하일 때만 밀도에 포함하고, 599·600·601초를 검사’는 확인 가능한 작업이다. ‘저장·비교·공유 전체’ 대신 ‘후보 네 개를 저장하고 새로고침 후 복원’처럼 관찰할 행동으로 나눈다.

| 단계 | AI가 하는 일 | 본인이 확인하는 것 |
|---|---|---|
| ① 작업 카드 | 목표, 관련 설계 절, 완료 조건, 변경 범위를 제안 | 무엇이 나와야 완료인지 이해한다. 정상·경계·실패 사례를 가능한 범위에서 하나씩 정한다. |
| ② 짧은 계획 | 현재 파일을 읽고 구현·검사 계획을 5줄 안팎으로 제시 | 요청보다 범위가 커지지 않았는지 본다. 새로운 비용·계약 변경이 있으면 별도로 판단한다. |
| ③ 구현과 자체 검사 | 코드와 필요한 검사를 만들고 실제 실행, 관련 오류 수정 | 일상적인 편집마다 끼어들지 않는다. 예상 밖 대규모 수정이나 외부 작업이 나오면 범위를 확인한다. |
| ④ 필요한 변경만 독립 검토 | Codex가 요구사항·변경 내역·반례를 읽고 검토 | 의견의 수가 아니라 실제로 실패하는 사례가 있는지 본다. |
| ⑤ 직접 확인 후 채택 | 확인할 화면·주소·입력·실행 방법을 안내 | 내가 직접 완료 조건을 재현한다. 통과하면 main에 반영하고 상태를 갱신한다. |

‘main’은 검증된 기본 코드 묶음인 브랜치다. 브랜치는 main을 망가뜨리지 않고 작업할 수 있는 별도 변경 흐름이다. main 반영과 공개 서버 배포는 별개의 단계로 취급한다.

작은 문구·간격 수정은 이미 목표가 명확하면 별도의 계획 승인이나 다른 모델 검토까지 거치지 않는다. 구현, 해당 화면 확인, 기본 검사로 마친다. 계산·데이터·서버 변경에는 다섯 단계를 적용한다.

작업 카드에 꼭 필요한 것은 다음 여섯 줄이다.

> 목표: 사용자가 하게 될 행동 또는 계산 하나
>
> 기준: v2.1의 관련 절
>
> 완료 조건: 내가 확인할 결과 2~3개
>
> 범위: 이번에 바꿀 부분 / 연결만 하고 남겨둘 부분
>
> 증거: 화면, 실제 응답, 검사 출력 중 필요한 것
>
> 미완료 조건: 무엇이 남으면 완료로 표시하지 않을지

AI가 제출할 완료 보고는 ‘변경 세 줄, 실제 실행한 검사와 결과, 미확인 사항, 사람이 따라 할 확인 순서’면 충분하다. 통과 결과는 로그나 검사 화면에서 확인할 수 있어야 한다. 도구 접근 제한으로 실행하지 못했다면 성공으로 계산하지 않는다.

**5. 걸어봄에서는 검증의 정답을 이렇게 만든다**

테스트는 정해진 입력에 기대한 결과가 나오는지 자동으로 확인하는 검사다. 픽스처는 그 검사에 반복 사용하도록 고정한 입력 데이터다. 회귀 검사는 새 수정 때문에 이전에 되던 행동이 깨지지 않았는지 확인하는 것이다.

검사는 두 종류로 나눈다. 작은 가짜 데이터로 규칙을 정확하게 검사하고, 실제 충청권 데이터로 연결과 현실성을 검사한다. 모의 OSRM 응답으로 계산 검사를 통과했다고 실제 OSRM 연결까지 성공한 것은 아니다.

| 걸어봄의 확인 대상 | 사람이 이해할 기대 결과 | 확인 담당·증거 |
|---|---|---|
| 시간 보정과 10분 경계 | OSRM 540초에 5/4.5를 곱하면 서비스 600초다. 보정 후 599·600초는 포함, 601초는 제외 | 본인이 숫자 예제를 확인. AI가 자동 검사와 실제 출력 제출 |
| 좌표·캐시 | 같은 4자리 격자여도 서로 다른 5자리 입력은 별도 계산 키다. 값이 우연히 같다는 이유로 같은 캐시라고 판단하지 않는다 | 키·호출 여부 검사. 공개 로그에 좌표를 남기지 않는 개발용 검사로 수행 |
| 밀도 추가 배치 | 첫 60개에서 도달 시설이 없고 61번째 한 곳만 도달 가능하면 최종 정확 개수는 1 | 구현 전 가짜 후보와 기대값을 고정. 실패 시 ‘집계 미완료’ 표시도 확인 |
| 실제 `/table` 연결 | 좌표 161개를 보내 목적지 160개의 1행 결과를 받는다 | 실제 고정 버전 OSRM 응답. 모의 응답으로 대체 불가 |
| GeoPackage 후보 조회 | R*Tree로 추린 결과가 작은 데이터의 전수 거리 계산 결과와 같다 | B가 위치·범위를 이해할 수 있는 표본, AI가 대조 출력 |
| 상태와 비교 | 불확실·미완료는 정상 숫자로 위장되지 않는다. 시간은 작은 값, 개수는 큰 값이 우세 | C가 의도적으로 만든 상태별 화면과 비교표 확인 |
| 실제 보행 결과 | 공주 표본 시설이 존재하고, 경로가 통행 가능한 길을 따른다 | B의 지도·현장 근거. 정확한 초 단위 수치를 API에서 복사해 정답으로 삼지 않는다 |
| 저장·공유 | 네 곳 저장·복원·삭제가 되며 다른 브라우저에서 링크를 열어 같은 좌표를 분석한다 | 본인 또는 C가 직접 실행. 새 데이터 버전에서는 숫자가 바뀔 수 있음도 구분 |

테스트를 작성하는 AI에게 정답 결정까지 통째로 맡기지 않는다. 특히 현재 구현의 출력을 그대로 저장해 ‘정답 파일’로 만들면 기존 오류가 고정된다. 작은 계산 예제는 사람이 손으로 확인하고, 실제 5좌표 표본은 B가 확인한 시설·상태·통행 가능성과 합리적인 범위를 기록한다. 특정 데이터 버전의 수치 스냅샷은 이후 변화 감지용으로 사용하되, 현실의 정답 증명과 구분한다.

중요한 계산 검사는 잘못된 조건을 넣으면 실제로 실패하는지도 한 번 확인하게 한다. 예를 들어 테스트의 임시 사본에서 ‘600초 포함’을 깨뜨리면 해당 검사가 실패해야 한다. 검사를 무력화한 수정은 채택하지 않는다. 사소한 UI 변경마다 이런 확인을 반복할 필요는 없다.

초기에는 타입 검사, 프론트 빌드, 계산·API의 중요한 자동 검사를 하나의 기본 검사 절차로 정리한다. 타입 검사는 API 숫자가 문자열로 바뀌는 등 연결 오류를 찾고, 빌드는 실제 배포 가능한 파일이 만들어지는지 확인한다. 초기 환경 구성 뒤부터 GitHub Actions에서 같은 기본 검사를 실행하게 한다. 이 자동 검사를 CI라고 부른다. 전국 데이터 생성·현장 검수·긴 부하 시험까지 매 변경마다 실행하지 않는다.

필요한 UI 검증을 먼저 수동으로 수행하고, Week 5~6에 반복 가치가 생긴 저장·비교·공유 핵심 흐름만 브라우저 자동 검사로 묶는다. 처음부터 모든 화면에 자동 테스트를 만들지는 않는다.

**6. 두 AI의 교차 검증은 중요한 변경에 집중한다**

| 변경 유형 | 기본 검증 |
|---|---|
| 문구·간격·단순 표시 | 작성자 검사 + 본인의 화면 확인 |
| 좌표·시간·캐시·밀도·상태·비교 계산 | 규칙 검사 + Codex 독립 검토 + 대표 결과 확인 |
| 데이터 변환·후보 추출·OSRM 연결 | 자동 대조 + B의 데이터 검수 + Codex 검토 |
| API 계약·버전 처리·저장·공유 의미 | 계약 검사 + Codex 검토 + 실제 사용자 흐름 |
| 외부 포트·비밀키·배포·데이터 교체 | Codex 검토 + 정확한 대상·복구 방법 확인 + 본인 배포 승인 |

검토자는 작성자와 다른 새 대화에서 시작한다. v2.1 관련 절, 작업 카드, 기준 커밋과 검토 대상 커밋, 실제 변경 내역, 검사 결과를 제공한다. 커밋은 특정 시점의 코드 변경을 저장한 기록이다. 작성자의 ‘문제없다’는 결론만 전달하지 않는다. 검토 중에 작성자가 수정하면 검토 대상이 바뀌므로, 수정 뒤에는 바뀐 부분을 다시 확인한다.

검토 요청은 ‘코드를 예쁘게 고쳐 달라’가 아니라 ‘완료 조건을 깨뜨리는 입력이나 오류가 있는가’로 한다. 코드 스타일 취향·가능한 미래 확장·새 기술 추천은 이번 검토에서 제외한다. 지적에는 입력, 기대 결과, 실제 결과 또는 코드 근거가 있어야 한다.

두 AI의 의견이 갈리면 투표하지 않는다. 같은 입력으로 검사하거나 공식 문서와 실제 실행 결과를 대조한다. 둘 다 확인하지 못한 것은 미확인으로 남긴다.

모델 선택도 세 단계면 된다.

- 빠른 모델·낮은 추론: 문구, 반복 수정, 이미 정해진 규칙의 단순 구현, 로그 요약. 로그 요약은 원문을 함께 보존한다.
- 기본 코딩 모델·보통 추론: 대부분의 기능 구현과 일반 오류 수정. 매 작업마다 최고 설정을 쓸 필요는 없다.
- 높은 추론: 계산 경계, 계약 모순, 데이터 손상 가능성, 배포·복구 검토, 재현했는데 원인이 불분명한 오류. 구현 전체보다 어려운 판단 구간에 집중한다.

모델 이름을 14주 동안 고정할 필요는 없다. 계정에 제공되는 모델을 이 역할에 배치한다. 공식 제공 옵션이나 사용량 조건이 바뀌면 확인하되, 매주 모델 비교를 별도 과제로 만들지 않는다.

**7. Git과 배포는 이 정도만 운용한다**

브랜치는 검증된 `main`과 현재 작업 브랜치 하나를 기본으로 한다. 한 작업이 끝나면 변경 제안인 PR을 만들고, 검사와 확인을 거쳐 main에 합친다. 이것을 병합이라고 한다. 본인이 유일한 개발자여도 PR은 ‘무엇을 채택했는가’를 보는 한 화면으로 유용하다. 다른 팀원을 형식적인 코드 승인자로 지정하지 않는다.

AI에게 브랜치 생성·커밋 정리·PR 초안까지 맡길 수 있다. 본인은 변경 파일 목록과 검사 결과를 보고 최종 병합을 결정한다. 아주 작은 문서·문구 수정은 같은 저위험 작업으로 묶어도 된다. main 직접 편집, 이력을 강제로 덮는 push, 이유를 모르는 일괄 삭제는 기본 흐름에서 제외한다.

진행 중 작업도 하루가 끝나면 작업 브랜치에 저장하고 GitHub로 올린다. 이것을 push라고 한다. 미완료 저장점은 가능하지만 검사 실패 상태를 완료로 표시하지 않는다. 저장하기 전에 비밀키·원본 개인정보·거대한 OSRM 파일이 포함되지 않았는지 파일 목록을 확인한다. `.gitignore`는 Git에서 제외하는 규칙일 뿐 AI가 파일을 읽지 못하게 하는 보안 장치는 아니다.

실패한 변경을 취소할 때에는 이미 저장된 변경을 되돌리는 revert를 기본으로 배우면 된다. 아직 저장하지 않은 작업을 없애야 한다면 AI에게 삭제 대상 목록과 보존할 것을 먼저 보여 달라고 한다. 돌아갈 수 있는 저장점을 만들기 전에 전체 초기화부터 실행하지 않는다.

본인은 Git 명령을 외우기보다 현재 브랜치, 바뀐 파일, 저장점, 원격 업로드 여부, 되돌릴 지점을 VS Code나 GitHub에서 찾을 수 있으면 된다.

배포는 main에 합친 뒤 별도로 실행한다. 배포 전 다음 네 가지를 확인한다.

1. 어떤 코드 커밋을 배포하는가.
2. 사용할 `data_version`과 `time_model_version`은 무엇인가.
3. 기본 검사가 그 변경에서 통과했는가.
4. 실패하면 어떤 코드·데이터 버전으로 되돌리는가.

GitHub Actions의 기존 배포 흐름은 사람이 실행 시점을 정하도록 시작한다. 서버는 v2.1대로 빌드·전처리 장소로 쓰지 않는다. 서버에서 직접 코드를 고쳐 문제를 끝내면 PC와 서버가 달라지므로, 수정은 저장소에 남겨 다시 배포한다.

배포 후에는 실제 도메인에서 작은 확인을 한다. 이를 스모크 테스트라고 한다. 초기에는 페이지와 API 응답, Week 3 이후에는 분석·경로, Week 6 이후에는 저장·비교·공유까지 이미 완성된 핵심 흐름을 확인한다. 데이터 교체 때에는 v2.1의 고정 5좌표 검사를 수행한다. 새 버전이 실패하면 직전 정상 버전으로 먼저 복구하고, 실패한 버전의 원인은 로컬에서 좁힌다. Week 8의 실제 복구 실습은 유지한다.

권한은 ‘문서에 하지 말라고 쓰기’와 ‘도구가 실제로 못 하게 설정하기’를 구분한다. 초기에는 Claude의 수동 승인/계획 모드와 Codex의 제한된 작업 권한으로 시작하고, 익숙해지면 프로젝트 안의 편집·기본 검사에 필요한 권한만 미리 허용한다. 승인된 작업 중 정상적인 편집마다 다시 허락을 받는 운영은 피한다. 운영 서버 작업·삭제·비용 발생·권한 확대는 별도로 확인한다. 권한을 전부 건너뛰는 모드는 기본 운영으로 쓰지 않는다. [Claude Code 권한 문서](https://code.claude.com/docs/en/permissions), [Codex Windows 권한 경계](https://learn.chatgpt.com/docs/windows/windows-sandbox)

운영 비밀키는 채팅에 붙이지 않고 서버나 배포 도구의 비밀값 설정에 직접 넣는다. 키 값 자체를 보여 주지 않고도 변수 이름과 설정 여부를 점검할 수 있게 한다. 노출됐다면 메시지나 Git 기록에서 지우는 것만으로 끝내지 말고 해당 키를 교체한다.

**8. 막혔을 때는 수정 속도를 낮추고 관찰을 늘린다**

일반 오류는 현재 저장소를 읽을 수 있는 구현 에이전트에게 먼저 진단시킨다. 별도 채팅에 오류 한 줄만 보내면 환경과 직전 변경을 추측해야 한다.

같은 실패가 두 번 반복되거나 약 45분 동안 새 증거 없이 같은 수정을 반복하면 다음 순서로 전환한다. 시간은 강제 중단 기한이 아니라 맹목적 수정 반복을 끊는 신호다.

1. **현재 상태 보존:** 브랜치와 변경 목록을 기록하고, 실패 로그를 남긴다. 관계없는 패키지 업그레이드·재설치를 중단한다.
2. **재현 입력 고정:** 어느 화면·주소·입력·명령에서 실패하는지 한 가지 사례로 좁힌다. 기대 결과와 실제 결과를 나란히 적는다.
3. **경계를 하나씩 확인:** 요청이 브라우저를 떠났는지, API에 도착했는지, 데이터 조회와 OSRM 중 어디까지 성공했는지 순서대로 확인한다.
4. **가설 하나만 검사:** 가장 가능성 높은 원인 하나와 그것이 맞을 때 관찰될 결과를 적고, 최소 확인을 수행한다.
5. **최소 수정·재검사:** 원래 실패 사례가 해결되는지 확인하고, 관련된 기존 동작도 한 번 확인한다. 해결 근거를 카드에 남긴다.

| 증상 | 먼저 확인할 곳 |
|---|---|
| 버튼을 눌러도 아무 변화 없음 | 브라우저 개발자 도구의 Network: 요청이 실제로 나갔는가 |
| API 주소로 직접 호출해도 실패 | FastAPI 오류·입력·설정. 화면 코드를 먼저 뜯지 않는다. |
| API 성공인데 숫자나 시설이 이상함 | 좌표 순서, 데이터 버전, 후보 목록, OSRM 원응답, 시간 보정 순서 |
| 로컬은 되는데 배포 서버만 실패 | 코드·이미지·데이터 버전, 환경변수의 설정 여부, 파일 경로 |
| 첫 분석만 느리거나 동시 요청에서 실패 | 캐시 미스 여부, OSRM 소요시간, 배치 수, 메모리. 새 DB를 먼저 도입하지 않는다. |

Network는 브라우저와 서버가 주고받은 요청을 보는 창이다. 처음에는 요청 주소, 성공·실패 상태, 응답 내용 세 가지를 찾는 정도만 배우면 된다. 로그는 프로그램이 남긴 실행 기록이다. 공개 로그에는 좌표·검색어를 남기지 않는 v2.1 규칙을 지킨다.

새 모델이나 ChatGPT Project로 넘길 때에는 다음 정보를 한 번에 전달한다: 현재 버전/브랜치, 관련 설계 절, 재현 단계, 기대·실제 결과, 관련 오류 원문, 이미 시도한 것과 관찰 결과, 아직 확인하지 못한 가설. 비밀값은 가린다. 이 자료는 AI가 초안을 작성하고 본인이 누락을 확인하면 된다.

한 작업 시간 전체를 써도 원인을 좁히지 못하면, Codex를 높은 추론으로 읽기 전용 진단에 투입한다. 실제 데이터의 통행·시설 문제라면 B에게, 사용 흐름 문제라면 C에게 넘긴다. 더 큰 모델도 사실을 확인하지 못하면 교수·조교·공식 지원 채널에 같은 재현 자료로 질문한다. 모델만 바꾸어 같은 전체 구현을 반복시키지 않는다.

**9. ChatGPT Project는 필요할 때만 쓰는 이해 보조 공간이다**

Project는 이 프로젝트의 설명 자료와 관련 대화를 묶어 두는 공간으로 사용한다. 작업마다 반드시 거치는 단계로 만들지는 않는다. 다음 상황에 사용한다.

- AI의 수정 이유를 읽었지만 어떤 결과 차이가 생기는지 이해되지 않는다.
- 계산식·캐시·좌표·배포 같은 처음 보는 개념을 이번 작업과 연결해 배우고 싶다.
- 두 AI가 다른 의견을 내는데 판단 기준이 필요하다.
- 진단 자료는 모였지만 다음에 무엇을 확인할지 모르겠다.

Project에 v2.1과 `PROJECT.md`를 두고, 중요한 변경 뒤에 최신본을 올린다. 현재 작업에는 최신 `STATUS.md`와 필요한 코드 변경·오류 자료만 첨부한다. 업로드한 파일이 로컬 저장소와 자동으로 같아진다고 가정하지 않는다. 답변에 사용할 기준 날짜나 커밋을 적는다. 문제 하나마다 대화를 새로 시작하고, 긴 대화의 결론 중 채택한 내용만 저장소에 반영한다.

Project에서 나온 조언은 후보안이다. 원문·실행 결과와 대조하고 작업 카드로 만든 뒤 구현 에이전트가 적용한다. 설명 채팅에서 받은 코드 조각을 여기저기 직접 붙여 넣는 운영은 피한다.

Project의 설명 요청 기준은 이것이면 충분하다.

> 나는 비전공자이며 걸어봄 v2.1의 범위와 기술 스택은 동결되어 있다. 지금 작업의 결과를 판단할 수 있게 설명해 달라. 용어는 뜻, 걸어봄에서 필요한 이유, 내가 확인할 행동을 연결해서 설명해 달라. 첨부하지 않은 현재 코드 상태를 아는 것처럼 말하지 말고, 확인된 사실과 추측을 구분해 달라. 필요한 경우 다음 확인 행동 하나를 먼저 제시해 달라.

**10. 배워야 할 것은 코드 전체가 아니라 검증할 경계다**

한 번에 한 개념을 15~20분 배우고, 바로 실행 화면이나 예제로 확인한다. 강좌를 먼저 완주한 뒤 구현을 시작할 필요는 없다.

| 개념 | 뜻·걸어봄에서의 역할 | 본인이 이해하면 충분한 수준 |
|---|---|---|
| 프론트·백엔드·API | 프론트는 화면, 백엔드는 서버의 처리, API는 둘 사이의 요청·응답 약속 | 오류가 화면 문제인지 응답 문제인지 구분하고 응답의 상태·숫자를 읽는다. |
| Git·브랜치·커밋 | 변경 이력, 작업 분리, 저장점 | 지금 작업 위치와 마지막 정상 저장점을 찾고 되돌림을 요청한다. |
| 테스트·픽스처 | 정해 둔 입력과 기대 결과로 동작 확인 | 테스트가 무엇을 증명하고 무엇은 증명하지 못하는지 말한다. |
| 좌표·단위·스냅 | 위치의 숫자·미터/초·보행망에 붙인 위치 | 경도/위도 순서, 계산 좌표, 원래 핀과 도로 위치의 차이를 확인한다. |
| 후보 추출·라우팅 | 가까운 시설을 먼저 고르고 보행망 경로로 비교 | 직선 후보 20개와 보행 최소 선택이 다른 단계임을 설명한다. |
| 캐시·버전 | 이전 결과 재사용과 사용한 데이터/규칙의 표식 | 데이터나 k를 바꿨는데 과거 결과가 섞이지 않는지 확인한다. |
| Docker·배포·환경변수 | 프로그램 실행 묶음·서버 반영·주소와 키 같은 설정 | 세 컨테이너 역할, PC/서버 구분, 버전, 키가 있는 위치를 안다. |
| 로그·Network | 프로그램 실행 기록·브라우저 요청 기록 | 실패 지점을 좁히는 증거를 찾고 민감값을 가린다. |

React 내부 동작, 고급 TypeScript 문법, OSRM의 MLD 알고리즘 내부, R*Tree 구현 원리, TLS 수학, Docker 내부 구조까지 공부할 필요는 없다. 해당 부분의 코드 작성은 AI에게 맡기고, 걸어봄의 입력·출력 규칙과 실제 검증 결과를 본다.

작업을 승인하기 전에 본인 말로 다음 문장을 완성해 본다: “이번 변경은 ___을 위해 필요하고, ___을 넣으면 ___이 나와야 하며, 그것을 ___에서 확인했다.” 배포 작업이라면 “실패하면 ___로 되돌린다”를 덧붙인다.

**11. B·C의 결과를 실제 개발 입력으로 받는다**

B에게 ‘데이터 검수 완료’ 한 줄을 받지 않는다. v2.1의 배포본 사양대로 `data_version`, 출처·기준일, 매핑표·수정표, 카테고리별 개수·결측, 검수한 표본, 아직 의심되는 위치를 함께 받는다. 정제·검증 스크립트는 AI가 만들고, B는 실행 안내를 따라 재현하고 표본을 확인한다. 코드 수정이 필요하면 개발 작업 카드로 넘긴다.

데이터는 원본 → 정제본 → 검수한 배포본을 구분해 기존 드라이브에 보관한다. 거대한 GeoPackage·OSRM 파일을 Git에 넣지 않고, 생성 방법·작은 검사 데이터·버전 기록을 저장소에 둔다. OSRM 이미지 태그와 배포 파일 세트가 맞는지 자동 확인하고, PC 검수에 사용한 버전과 서버 버전을 대조한다. 스키마가 맞는다는 자동 검사만으로 시설 존재·통행 가능성이 확인된 것은 아니다.

C의 버그 카드는 다음 여섯 항목이면 된다: 사용한 배포 버전/일시, 기기·브라우저, 재현 단계, 기대 결과, 실제 결과, 캡처나 짧은 영상. 오류마다 긴 보고서를 작성할 필요는 없다. 수정한 사람의 시연만 보고 닫지 말고 C가 같은 순서로 다시 실행해 닫는다.

본인이 검수할 수 없는 GIS 사실은 B의 확인을 받아야 하고, C의 테스트 결과가 없으면 사용자 테스트 완료라고 표시하지 않는다. AI가 팀원의 현실 검증을 대신했다는 문구를 쓰지 않는다.

**12. 14주 일정 위에 얹을 주간 루틴**

v2.1의 Week 6 핵심 완성, Week 8 베타, Week 10 안정판, Week 11 버퍼를 그대로 유지한다. 운영 준비를 별도 몇 주짜리 사전 과정으로 만들지 않는다.

주 22시간을 기준으로 구현 약 12시간, 검증·QA 약 4시간, 문제 해결 여유 약 3시간, 필요한 학습 약 2시간, 월·목 회의 합계 1시간을 배치한다. 기록과 작업 지시는 해당 작업 시간에 포함한다. 고정 비율이 아니라 출발점이며, 초기에는 구현 시간을 일부 학습·환경 확인으로 옮긴다. 실측·사용자 테스트가 있는 주는 그만큼 다른 작업 시간을 줄여 계산한다.

월요일에는 이번 주 완료할 결과를 2~3개 정한다. 화·수에는 한 번에 한 작업씩 구현·검증한다. 목요일에는 B·C의 결과로 잘못된 방향을 확인한다. 금요일에는 실제 동작을 함께 보고 검증된 변경을 배포하며 다음 작업을 정한다. 배포할 변화가 없으면 억지로 배포하지 않는다.

매일은 시작 10분에 상태·브랜치·오늘 작업을 확인하고, 가장 집중할 시간에 구현 한 묶음을 맡긴다. 완료 뒤 30~60분은 직접 확인할 시간으로 남겨 둔다. 필요한 개념 하나를 배우고, 종료 10분에 저장·원격 업로드·다음 작업을 기록한다. 하루 종일 AI를 실행하고 검수를 다음 주로 미루지 않는다.

**14. 내일부터 움직일 순서**

첫날의 목표는 기능을 많이 만드는 것이 아니라 ‘두 AI가 같은 기준을 읽고, 내 PC에서 작업하고, 확인한 결과를 저장하고 되돌릴 수 있다’는 상태를 만드는 것이다.

1. **v2.1을 기준 파일로 지정한다.** 기존 v1·v2는 참고 자료로 분리한다. ChatGPT Project에도 v2.1을 올리고, 제품 재설계보다 이해·진단을 돕도록 지침을 정한다.
2. **내 PC 상태를 먼저 확인한다.** 운영체제·메모리·디스크·기존 도구를 AI가 읽기 전용으로 조사하게 한다. VS Code와 공식 Claude Code·Codex 확장을 사용할 환경 하나를 정한다. 아직 불필요한 도구를 일괄 설치하지 않는다.
3. **GitHub 저장소 하나와 작업 폴더 하나를 연결한다.** 공통 지침과 작은 운영 파일을 AI에게 초안 작성하게 하고, 두 도구가 같은 기준을 읽는지 확인한다. 실제 실행 방법은 확인된 것부터 README에 기록한다.
4. **저장·복구를 연습한다.** 연습용 문서 한 줄을 수정해 변경 내역 보기, 커밋, 원격 업로드, 되돌리기를 수행한다. 이 한 번은 직접 화면을 보며 익힌다.
5. **첫 작업 카드는 HTTPS 빈 페이지다.** 공개 주소에서 ‘걸어봄’이 보이는 것을 완료 조건으로 둔다. 배포 설정과 대상은 설명을 확인한 뒤 실행한다. 설치가 막히면 같은 날 안에 억지로 완료했다고 처리하지 않는다.
6. **B·C에게 다음 입력을 요청한다.** B는 데이터 출처·파일·기준일 목록과 공주 대표 위치, C는 게이트 1의 카카오 문의 자료와 테스트할 사용자 흐름을 준비한다. 실제 연락·계정 작업은 팀이 수행한다.
7. **종료 때 다음 작업 하나만 남긴다.** 게이트 1 상태와 아직 확인하지 못한 항목을 적고, Week 2의 첫 계산 작업을 준비한다. 일반 기능 구현은 v2.1의 착수 조건에 맞춘다.

v2.1은 9월 7일 시작 일정이므로 지금은 Week 1 중간이다. 새 운영 준비를 이유로 14주 일정을 다시 시작하지 않는다. 남은 Week 1에서는 위 준비와 게이트를 우선하고, 미완료 항목은 숨기지 않고 다음 작업에 반영한다.

시작 전에 한 문장만 정정할 사항도 있다. v2.1 4-3의 설명 중 ‘sources/destinations를 생략한 161×161 행렬이 max-table-size 200을 초과한다’는 부분은 산술상 맞지 않는다. 161²은 200²보다 작다. **설정 200은 유지하고, FastAPI의 목적지 가드와 실제 1×160 응답 검사를 안전장치로 사용한다**고 설명만 고치면 된다. 제품·아키텍처 변경 사안은 아니다. [OSRM 제한 검사 소스](https://github.com/Project-OSRM/osrm-backend/blob/v5.27.1/src/engine/plugins/table.cpp)

첫날 끝에 확인할 것은 네 가지다: 기준 문서가 하나인가, 작업 폴더와 저장점을 찾을 수 있는가, 직접 확인한 결과가 있는가, 내일 할 작업 하나가 정해졌는가.
